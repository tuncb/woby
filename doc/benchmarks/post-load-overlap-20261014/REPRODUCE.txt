The analysis uses:
- The recorded native model.add RPC interval for full-load time. This excludes
  the observer's later discovery that the request is complete.
- Trace marks for first GPU frame and full readiness.
- post_load_cpu_total for the joined CPU work. Do not add overlapping phases.
- Process peak commit and working set for the full run.
- Sampled private bytes and working set between first GPU frame and readiness.
- The first three seconds of recorded camera motion, after the first moving
  frame, for the matched preparation-time navigation comparison.
- A separate 24-command camera-orbit recording after readiness.

Camera motion measures frame cadence under load. It does not measure physical
input-to-display latency. GPU timings can trail CPU submission. Memory samples
have a requested 100 ms period; the summary retains their actual intervals.
Three runs show repeatability on this machine, not performance on all hardware.

Worker limit:
  hardware > 3 ? min(8, hardware - 3) : 0
hardware is std::thread::hardware_concurrency(), the logical CPU count.
The measured Ryzen 7 5800H has 8 cores and 16 logical CPUs, so the cap is eight
helper threads. Callers also do work. This cap is shared by analysis helpers,
including nested preparation; it is not a limit on all application threads.
The outer post-load split can take one helper slot. The remaining slots serve
nested work. If no slot is available, the caller drains the task queue.

The cap was introduced in commit 89a4e933d278e56e7b387590eb6c631c18f7aa77.
The source states that it leaves capacity for the UI and other threads. No
recorded tuning study was found for the choice of eight. This experiment keeps
the cap unchanged. To tune it separately, compare caps such as 2, 4, 6, and 8
with the same load, memory, and camera-motion measurements.
