BearTrap: start annotations with the other post-load work

14 October 2026 · Release · Baseline f8bd1e4 · Three runs per build and capture mode

Post-load CPU work during visible camera motion changed from 7.568 s to 6.801 s (10.1% less time). Post-frame peak commit stayed near 8.08 GiB. The P99 CPU frame time rose from 20.539 ms to 23.103 ms, while the frame rate stayed near 57 FPS.

This experiment reduces preparation time with a measured cost in the tail of the frame-time distribution. The per-run ranges overlap. Keep this uncertainty when judging the three-run result. Native full-readiness medians were 22.015 s and 19.236 s; earlier, unchanged loading stages also varied. The tables below separate these measurements.

The current baseline already runs point preparation alongside annotations. This change also overlaps source-index mapping and original bounds with annotations. Both tasks use the same immutable geometry snapshot and shared helper limit. They join before the point upload. Full readiness still requires both CPU results and the completed upload. Stale results are rejected before publication.

The earlier report used revision 7ee6133. Its 20.6-second CPU sequence and 10.9-second ideal overlap limit are not the baseline for this comparison. Later commits already changed the preparation costs. The ideal limit was not a predicted result.

Navigation control

The generated trace viewer calls the normal UI camera operation at 30 degrees/second while preparation is pending. The production viewer has no added motion code. The comparison uses the first three seconds after the first moving frame. A separate recording sends 24 camera-orbit commands after readiness.

These controls measure frame cadence during motion. They do not measure physical input-to-display latency. GPU timing can trail CPU submission. Hidden windows were paced at 20 FPS. A separate set of three visible-window pairs tests active rendering. All captures use a 1280×720 drawable, fresh processes, and a warmed copy of the same 7,108,991,827-byte OBJ. They run in rotating or alternating order without concurrent builds, tests, or profilers. Three runs do not establish results for other hardware.

Worker limit

hardware > 3 ? min(8, hardware - 3) : 0, where hardware is the logical CPU count reported by std::thread::hardware_concurrency(). This Ryzen 7 5800H has eight cores and 16 logical CPUs, so the cap is eight helper threads. Calling threads also do work. The cap is shared by simultaneous and nested analyses; it is not a limit on all application threads.

The post-load split can reserve one helper slot for its second task. Nested operations share the remaining slots. Small operations and operations without free slots run on their caller. The cap was introduced in commit 89a4e93 to leave capacity for the UI and other threads. No recorded study was found that selects eight as the best value. This change leaves the cap unchanged.
