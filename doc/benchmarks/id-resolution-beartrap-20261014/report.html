BearTrap: faster serial ID resolution

Serial ID resolution falls from 5.963 to 2.893 seconds in matched application traces. This saves 3.070 seconds, or 51.5%.

First display and full readiness each advance by about three seconds in those traces. Native production controls show a median paired readiness gain of 3.699 seconds. Global IDs in order of first use, triangle order, group UV flags, and the 12-byte primary table are retained.

Input: 7,108,991,827 bytes; 227,315,958 triangle corners; 37,890,645 positions; 38,414,391 render vertices. The original measurement is in the end-to-end report.

What changed

The primary table layout stays at 12 bytes per source position, or 433.62 MiB for BearTrap. The resolver reads the source-position count once. It accumulates the invalid-UV bit with an integer OR and tests it once per group.

The caller selects eager or deferred source-index writes and the finite or fallback UV path once. The compiler removes those fixed choices from each corner iteration. This reduces branch and register work in the application loop.

A sequential UV scan checks the float values used by the renderer. If every value is finite, primary ID creation no longer reads UV coordinates through each first-use key. The scan uses no large buffer and polls cancellation on the caller. A scan is skipped if there are more UV records than corners.

If the scan does not pass, the resolver prefetches UV data 32 corners ahead. Lookahead stays within the current shape. Missing UVs and out-of-range prefetch addresses are skipped. Normal and UV seam keys still use the existing secondary table.

Experiments and decisions

Table-only prefetch did not improve BearTrap. Padding to 16 bytes, packed attribute pairs, reordered fields, and split arrays gave small gains or regressions. The 8-byte UV-only prototype saved memory but added a layout variant for a small further time gain. The selected design keeps the existing table and gather code.

Prefetching UV data produced the first large gain. A finite-UV scan removed more dependent reads. Continuing to prefetch after a successful scan made the resolver slower, so the final resolver disables that work. A parallel resolver was not required for this result; ordered ID assignment remains serial.
